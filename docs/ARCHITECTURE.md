# Architecture of the video subsystem

A guided tour of Mumble Video's pipeline: capture → encode → network → decode → render, the threading
model, and where this fork meets upstream Mumble. [`README.md`](../README.md) says what the product
does; this says how. [`CONTRIBUTING.md`](CONTRIBUTING.md) says how to build, test and measure it.

Everything here was read off the code. Where a design has a reason that is not obvious, the reason is
given — usually because getting it wrong once is how the reason was learnt.

---

## The shape of it

Four layers, from the bottom:

```
┌─ src/mumble-core/ ────────────── Qt-free protocol library ───────────────────┐
│  crypt state · fragmentation · reassembly · media demux · control framing    │
│  No Qt. No sockets. No Mumble globals. The Android app links this directly.  │
└──────────────────────────────────────────────────────────────────────────────┘
          ▲                                                      ▲
          │ used by                                              │ used by
┌─────────┴──────────────────┐                      ┌────────────┴────────────┐
│  src/murmur/  (the server) │                      │  src/mumble/ (the client)│
│  routing, permissions      │◀──── UDP + TCP ─────▶│  capture, encode,        │
│  relay, keyframe limits    │                      │  decode, render, UI      │
└────────────────────────────┘                      └─────────────────────────┘
```

The core is the one seam that is genuinely enforced: CI configures `src/mumble-core` standalone in a
job where nothing can find Qt, with `-Wall -Wextra -Wsign-conversion -Werror`
([`.github/workflows/build.yml`](../.github/workflows/build.yml)). That is why it has stayed clean. Its
wire format is additionally pinned by known-answer vectors under `src/mumble-core/test-vectors/`,
generated by an independent Python implementation, so a change to the encoding fails a test rather than
breaking a peer.

## Capture

Everything that produces pixels implements one interface, `VideoSource`
([`src/mumble/VideoSource.h`](../src/mumble/VideoSource.h)):

```cpp
bool start();  void stop();  bool isRunning();  QString describe();  void setMaxFramerate(unsigned);
signals:  frameReady(const QImage &, std::uint64_t captureTimestampUsec)
          captureIdle(std::uint64_t captureTimestampUsec)
          failed(const QString &reason)
```

| Backend | Platform | How it gets frames |
|---|---|---|
| `CameraVideoSource` | all | Qt Multimedia, event-driven. Avoids MJPEG where the device offers an alternative. |
| `DxgiDisplayVideoSource` | Windows | DXGI Desktop Duplication: a whole output. Polled on a timer. Composites the cursor itself. |
| `WgcWindowVideoSource` | Windows | Windows.Graphics.Capture: one window, through the raw COM ABI. Polled. |
| `PipeWireScreenVideoSource` | Linux | The XDG desktop portal picks the target; frames arrive over PipeWire on PipeWire's own thread. The only way capture works on Wayland. |
| `X11ScreenVideoSource` | Linux | `XShmGetImage` of a rectangle of the root window, on a capture thread of its own. The fallback when no portal answers. |
| `CroppedVideoSource` | all | A decorator: wraps any source and re-emits `frame.copy(region)`. This is how region sharing works everywhere at once. |
| `SyntheticVideoSource` | all | `MUMBLE_MOCK_*`: a deterministic desktop or film-like footage. The reason any of this can be tested without hardware. |

Three things worth knowing:

- **`captureIdle` is not a failure.** Duplication and PipeWire both report "nothing changed" as an
  ordinary, frequent outcome. It drives the still-screen handling downstream.
- **`failed()` is delivered through a queued connection**, deliberately, at every backend. A source
  that destroys itself inside its own `failed()` handler is a use-after-free, and that was found the
  hard way.
- **`captureTimestampUsec` is microseconds since that capture source started**, not a wall clock. It
  travels with the frame all the way to the receiver, which only ever uses *differences* of it. Anything
  that treats it as absolute is wrong — see the paint-delay measurement below.

### Why region sharing is a decorator

Every backend hands its frames to the same `frameReady`, so cropping above them costs nothing per
platform and is strictly cheaper than the share it crops: fewer pixels reach the encoder. On X11 nothing
is cropped at all, because `X11ScreenVideoSource` already grabs whatever rectangle it is given.

The conversion from the drag to capture pixels lives in `CroppedVideoSource::toCapturePixels` and is
tested, because a drag happens in device-independent pixels while a backend produces the display's real
ones. It converts **edges**, not an origin and a size, so two boxes that shared an edge still share it;
and it clamps to the frame and **never widens**, because falling back to the whole frame would quietly
share more of the screen than was selected.

## Encode

```
VideoSource ──frameReady──▶ VideoBroadcaster ──(queued)──▶ VideoEncodeCore ──▶ one of three encoders
                              │                              on "VideoEncode"
                              │ decides: target size, stream id, frame drops, keyframe forcing
                              ▼ unitReady(VideoUnitHeader, QByteArray)
                           MainWindow lambda ──▶ ServerHandler::sendVideoUnit
```

`VideoBroadcaster` ([`VideoBroadcaster.h`](../src/mumble/VideoBroadcaster.h)) is the send half, and it
exists as its own class so the encode-and-emit behaviour can be tested against a synthetic source with
no camera, no window and no network. It knows nothing about sending.

`VideoEncodeCore` is split out of it so it can live on the encode thread. Its contract is stated in its
header: **every method is called from one thread at a time, whichever one that is, so it needs no locks
of its own.** Reaching it from elsewhere goes through `withCore()`, which queues onto that thread.

| Encoder | Used for | Notes |
|---|---|---|
| `H264Encoder` | screen shares, when a hardware encoder opens | FFmpeg: `h264_nvenc`, `h264_amf`, `h264_mf` on Windows; `h264_vaapi`, `h264_nvenc` on Linux. Probed once with a 256x144 open. A frame may span up to 32 units. |
| `VpxEncoder` | cameras (VP8); screen shares with no hardware encoder (VP9) | libvpx. VP9 runs in `VP9E_CONTENT_SCREEN` mode with cyclic refresh. One frame is one unit. |
| `TiledImageEncoder` | nothing, in production | The original screen codec: independent JPEG tiles. Still *decodable*, because a peer may send it, but no sender here selects it. |

Codec choice is `screenShareCodec()` in [`MainWindow.cpp`](../src/mumble/MainWindow.cpp): hardware
H.264 when the setting allows and an encoder opens, VP9 otherwise. Cameras are always VP8.

Two numbering schemes reach the logs under the same field name, which is a trap worth naming:
`VideoBroadcaster::CODEC_*` is `VP8=0, TILED=1, H264=2, VP9=3`, while the wire enum in `Mumble.proto` is
`unknown=0, tiles=1, VP8=2, VP9=3, AV1=4, opus=5, H264=6`. The `VideoStats tx` line prints the first and
`VideoStats rx` prints the second.

### The frame size is decided before encoding

`targetSizeFor()` / `encodeSizeFor()` apply both a ceiling and a floor:

- **Ceiling**, because receivers refuse frames beyond their surface bound, so a 5120x1440 dual-monitor
  share is scaled down once here rather than encoded, sent and discarded.
- **Floor**, because a hardware H.264 encoder refuses to open below roughly 145x49 and treats the
  refusal as final. A 190x40 sliver of a toolbar was announced, carried nothing, and left viewers asking
  for a keyframe until their tiles gave up. Below the floor the frame is **centred on black**, not
  stretched: somebody asked for those pixels.

### A still screen stops being encoded

Under constant bitrate an encoder spends its whole budget refining an unchanged picture — measured at
the full 3 Mbit/s for VP9 on a still 1080p screen — and some backends keep delivering frames while
nothing changes. So an unchanged picture is encoded for one second, then not again until it changes,
with a keep-alive every two.

## Network

```
EncodedVideoUnit ──▶ VideoFragmenter ──▶ VideoCryptState::encrypt ──▶ UDP datagram (<=1200 bytes)
   (up to ~275 KB)      1098-byte payloads        OCB2-AES128, own key
```

Video shares voice's UDP socket, marked by a **media-channel byte**: `0x00` is voice, `0x01` is video
([`VideoTransport.h`](../src/mumble-core/VideoTransport.h), `MediaDemux`). That byte is why this client
and a stock Mumble server cannot speak UDP to each other, and it is the one incompatibility in the fork.

Video has its own crypt state, its own sequence space and its own datagrams, so a lost or replayed video
packet never touches voice's crypt state. The key and the two nonce bases are derived with SHA-256 from
the voice session key under three distinct labels; each end takes the opposite nonce base, so the two
directions agree without any exchange and never share one. The sequence number *is* the nonce, so it is
implicitly authenticated; encryption **refuses rather than wrapping** at `0xFFFFFFFF`; and the replay
window advances only after the tag verifies, so a forgery cannot punch a hole in it.

**This is new cryptographic code and it has had no independent review.** Its own header says so.

### The server hop

```
Server::run()  [one UDP thread]
  → MediaDemux: channel byte
  → relayVideo()        decrypt under the sender's crypt state
                        VideoRouter::subscribersOf()  ← re-checks ShareVideo and ReceiveVideo
                                                        for every recipient, on every packet
                        append the sender_session varint  (not a reserialise)
                        re-encrypt per recipient, sendmsg
```

`VideoRouter` ([`src/murmur/VideoRouter.h`](../src/murmur/VideoRouter.h)) is the one place to look for
the security property, which its header states: **a subscription is an authorisation decision re-checked
on delivery, not a lookup.** Permission checks are injected as callbacks, which is why the routing logic
is testable without a server at all (`TestVideoRouter`).

`VideoRouter` holds no locks of its own. Callers must hold `Server::qrwlVoiceThread` — write lock from
the TCP thread, read lock from the UDP thread. `docs/dev/MurmurLocking.md` is upstream's statement of
that discipline and predates this class.

### Loss recovery

Two independent mechanisms, and they escalate:

1. **Fragment-level, automatic.** A unit incomplete for 25 ms is named in a `VideoNack` — by a 64-bit
   mask for up to 64 fragments, by explicit indices beyond that, because re-sending a whole
   100-fragment keyframe loses another fragment as often as not under the very loss that caused the
   request. Up to three attempts, 150 ms apart. An attempt counts only once the request has actually
   been **sent**, not when it was considered: the caller batches requests into messages and drops what
   will not fit its caps, and counting too early meant a unit could spend all three attempts without one
   request leaving the host.
2. **Frame-level, from the display.** `VideoGrid` holds later frames for up to 700 ms waiting for a
   re-sent predecessor, then gives up and asks for a keyframe — over TCP, rate-limited to one per second
   per stream at both ends.

`VideoNack` deliberately rides UDP, because under packet loss TCP holds every later message back until a
lost segment is retransmitted.

**There is no congestion control.** The sender transmits at its configured bitrate whatever the path can
carry. `VideoSubscribe` reserves `observed_loss_permille`, `last_complete_frame` and
`preferred_bandwidth` for the feedback that would drive one; nothing fills them in. Measured
consequence: on a 2 Mbit/s path a 6 Mbit/s share delivers **no complete frames at all**.

## Decode and render

```
ServerHandler  [network thread]
  socket read → decrypt → replay window → VideoReassembler
      │ videoUnitReceived   (queued, to the GUI thread)
      ├──────────────▶ VideoStreamDispatcher ─▶ AudioOutputScreenShare   (share audio)
      ▼
  VideoGrid::onVideoUnitReceived          [GUI thread]
      ordering, hold-across-gap, retransmit requests
      │ (queued)
      ▼
  decode + YUV→RGB                        ["VideoDecode" thread]
      │ (queued)
      ▼
  presentFrame → playout queue → applyDecodedTile → paint   [GUI thread]
```

`VideoGrid` ([`VideoGrid.h`](../src/mumble/VideoGrid.h)) is the receiver. It is large — about 3,700 lines
of `.cpp` — because it currently does nine jobs: per-stream receive state, frame ordering and loss
recovery, decode orchestration, playout scheduling, surface compositing, grid layout and hit-testing,
the per-tile control bars, the fullscreen and picture-in-picture windows, and the diagnostics. Its
header's comments are worth reading before changing it; most of them record the specific crash that
motivated the guard they sit above.

**`VideoGrid` contains no reference to the `Global` singleton, and that is load-bearing.**
`TestVideoGrid` compiles it standalone against Qt, libvpx and `shared`, and nothing else. Keep it that
way: pass things in, or emit a signal.

### The playout buffer

Each surface estimates the smallest `(arrival − capture)` it has seen over a rolling ten-second window —
which, because the capture timestamp is not a wall clock, is mostly the constant offset between the two
processes' clocks plus the minimum transit. A decoded frame is then shown at
`capture + offset + delay`, and `delay` is measured rather than fixed.

The buffer exists to hold a frame long enough for a re-sent fragment to arrive before the frame was due.
It used to be a flat 200 ms, charged to every frame of every stream whether anything had been lost or
not — the largest single term in receiver latency, and on a clean link entirely wasted. The reason it
can be measured instead is that **a retransmission is already visible in the arrival times**: a frame
whose fragment had to be re-sent arrives late, and lateness is exactly `arrival − capture` relative to
the minimum. So no round-trip estimate, no loss detection and no second mode is needed. See
[`PlayoutDelay.h`](../src/mumble/PlayoutDelay.h):

    delay = clamp(20 ms, p99(lateness) + 10 ms, 200 ms)

over the same two ten-second windows, in a histogram that allocates nothing. The ceiling is the old
constant, so a path that genuinely needs 200 ms still gets it. Three properties matter more than the
formula: it **rises at once and falls slowly** (needing more buffer is urgent, needing less is not, and
re-timing a picture under the viewer is the stutter the buffer exists to prevent); it **will not believe
a percentile of three samples**, so there is a sixty-frame warm-up at the old 200 ms; and a **smaller
minimum transit discards the histogram**, because a smaller minimum means the clock relationship changed
and lateness measured against the old one is a measurement of nothing.

### Geometry from the wire is not trusted

`x` and `y` arrive from a peer. For a whole-frame codec the frame covers the surface, so the only
legitimate value is the origin, and anything else is refused — a non-zero position would have the frame
painted into a canvas grown to fit the claim, which at the surface bound is 33 MB held and a full-frame
copy on the GUI thread for every frame of the share. Canvas growth is bounded by `MAX_SURFACE_WIDTH` and
`MAX_SURFACE_HEIGHT` regardless.

### Share audio

A screen share's audio is a second stream beside the picture, announced with codec `OpusAudio` so it
rides the same per-sender subscribe, route and crypto path rather than the voice pipeline, which has no
room for a second stream per session. `VideoStreamDispatcher` listens to the same signal as `VideoGrid`,
in parallel, and neither knows the other exists; it hands Opus units to `AudioOutputScreenShare`, which
reorders, reconstructs with Opus in-band FEC, conceals what it cannot reconstruct, and corrects drift.

A share's audio is subscribed **only while that sender's picture is being watched**, as in Discord. So
unwatching a share stops its sound with no code of its own, and that is why hiding other people's video
needed none either.

## Threading model

| Thread | Created | Owns |
|---|---|---|
| GUI / main | Qt | `VideoGrid` (all of it), `VideoBroadcaster`, `ScreenAudioBroadcaster`, `VideoStreamDispatcher`, `MainWindow` |
| `"VideoDecode"` | `VideoGrid` | `VpxDecoder`, `H264Decoder`, and the YUV→RGB conversion |
| `"VideoEncode"` | `VideoBroadcaster` | `VideoEncodeCore` and the three encoders |
| `"X11ScreenCapture"` | `X11ScreenVideoSource` | Xlib and MIT-SHM. The object is `moveToThread`'d onto it. |
| PipeWire loop | PipeWire | the stream, the negotiated format, the pending frame |
| PulseAudio mainloop | PulseAudio | share-audio capture streams |
| WASAPI worker | `Wasapi*LoopbackSource` | the blocking capture loop |
| Audio mixer (real-time) | upstream `AudioOutput` | `AudioOutputScreenShare::prepareSampleBuffer` |
| Server UDP thread | `Server::run()` | `relayVideo`, and reads of `VideoRouter` |
| Server TCP/main | Qt | `msgVideoState`, `msgVideoSubscribe`, and writes to `VideoRouter` |

Rules this code follows, and which a change should keep following:

- **No lock is held across a signal emission.** PipeWire copies the frame under its mutex, closes the
  scope, *then* emits. The server closes the crypt scope before `sendmsg`.
- **Lock order on the client audio side is stated in the header**: `AudioOutput::qrwlOutputs` outside
  `AudioOutputScreenShare::m_mutex`.
- **The network→GUI boundary is explicitly `Qt::QueuedConnection | Qt::UniqueConnection`**, with a
  comment on why both halves matter.
- **`PipeWireScreenVideoSource.h` annotates each member with the thread that owns it.** That is the
  standard to match for anything new that is touched from two threads.
- `MUMBLE_VIDEO_UNTHREADED=1` runs encode and decode on the GUI thread, as the tests do. Useful for
  deciding whether a problem is a threading problem.

## Where this fork meets upstream Mumble

The video feature is about 43,000 lines, and it is in **153 new files**. The part that touches upstream —
the part that decides how hard the next upstream merge is — is about **6,000 added and 800 removed lines
across 83 existing files**. Keeping that ratio is the single most useful discipline in this repository.

The upstream files carrying the most fork change, and so the ones to be careful in:

| File | Why it is touched |
|---|---|
| `src/mumble/MainWindow.cpp` | the video control plane: share actions, pickers, stream ids, audio subscriptions, "who is watching", reconnect survival. About a quarter of the file. |
| `src/murmur/Server.cpp` | `relayVideo`, `relayVideoNack`, `sendVideoPlaintext`, subscription revalidation. Upstream's hottest server file. |
| `src/mumble/ServerHandler.cpp` | the video send and receive framing on the UDP socket. |
| `src/murmur/Messages.cpp` | `msgVideoState`, `msgVideoSubscribe`. |
| `src/mumble/CMakeLists.txt` | the new sources and the three fork options. |

A new capture backend, a new codec, or a new receiver behaviour should all be reachable without editing
any of those beyond a call site. Where that is not true today, it is a known cost rather than a design.

### Protocol changes are append-only

[`src/mumble-core/Mumble.proto`](../src/mumble-core/Mumble.proto) is proto2, where enums are closed:
enumerator 0 of every video enum is deliberately inert, so a peer that does not know a new value reads
`CODEC_UNKNOWN` and **drops the stream** rather than decoding it as whatever happened to be first. Add
values, never renumber.

## Measuring it

The pipeline reports on itself when asked. `MUMBLE_VIDEO_STATS=1` logs every two seconds:

- `VideoStats tx` — frame rate, bitrate, encode time mean and worst, units per frame, dropped frames.
- `VideoStats rx` — units, tiles and frames painted, the worst gap between paints, keyframe requests and
  why, recovered and abandoned gaps, and `paintDelayMs` percentiles.
- `VideoNackStats` — retransmission requests sent, answered, and how often the sender no longer held it.
- `GuiLag` — how late a 10 ms timer fired on the GUI thread. This is what stutter is, measured.

`paintDelayMs` is arrival-to-paint above `arrivalFloorMs`, the smallest arrival delay seen in a window.
It is the receiver's share of glass-to-glass and not the whole of it: the sender's capture-to-send time
sits below that floor and cannot be seen from the receiving process.

`MUMBLE_VIDEO_DUMP_TX` and `MUMBLE_VIDEO_DUMP_RX` write the frame the encoder was handed and the frame
the decoder produced, named by the sender's frame number — the same numbers the receiver sees, so a pair
is matched exactly. That is what makes VMAF, PSNR and SSIM possible at all; two screenshots of two
differently sized windows are not a comparison.

[`dev/mock-video-sources.md`](dev/mock-video-sources.md) for the full list of knobs.
