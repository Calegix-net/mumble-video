# Lag investigation — 2026-09-15

Four measured tracks against the live server `calegix.com:64738` (server image
`aa81b8b68` = the `dev-latest` MSI), plus a read-only code audit
([lag-audit-2026-09-15.md](lag-audit-2026-09-15.md)). Evidence on calegix under
`~/mumble-fork/lag-test-2026-09-15/{windows,linux,server,remote}/`. Every number
below is measured unless marked *inferred*.

## What the users call lag is three different things

| Where | Symptom | Cause | Status |
|---|---|---|---|
| Server | black rectangles on static regions, up to 2 s | UDP receive buffer clamped by `net.core.rmem_max` | **fixed on calegix**, code follow-up in this branch |
| Receiver (Chromebook) | whole picture stalls, camera freezes 1–2 s at a time | client cannot drain its socket under send+receive load; VP8 freezes until a keyframe | open, client work |
| Sender, heavy scenes | effective fps silently drops (15/10/7) | entire capture→encode path on the GUI thread | open, client work; not reproduced on a 1280x800 desktop |

The transport itself is fast. Real Windows DXGI capture → server → Linux receiver,
all on calegix, paired framebuffer screendump vs receiver screenshot on one
clock: **glass-to-glass median 40 ms, p90 56, max 83 at 57.6 fps**, zero stalls
(14 pairs pre-fix, 12 post-fix: 39 / 69 / 71). Linux→Linux relative to the
sender's own preview: median 3 ms at 31 fps. The relay adds p50 0.06 ms / p99
0.17 ms on loopback, and fans a whole burst out to two viewers within p90 5.7 ms.
Windows capture on a WARP-only VM adds nothing measurable.

## 1. Server: the rmem_max clamp (fixed)

`Server.h:199` requests 4 MB UDP buffers. calegix had the Fedora default
`net.core.rmem_max = 212992`; the kernel clamps silently and `setsockopt` still
returns 0, so `Server.cpp:213` "Failed to enlarge" never fired. Effective
buffer: **rb 425984** (`ss -unm`). A frame is sent as one unpaced burst of up to
408 datagrams (~2.3 KB skb truesize each), the buffer holds ~185, so every
keyframe overflowed:

- 19:05–19:12, two senders: **6,182 of 1,763,167 datagrams dropped (0.35 %)**,
  worst 5 s window 441, buffer occupancy peaking at 421,312 of 425,984.
- four streams: **+1,656 drops in 30 s** (~55/s), 32,114 on the counter by the
  time it was fixed.
- each drop loses a whole 128 px tile of a *static* region until the ≤2 s
  refresh: that is the black patch.

Fix: `/etc/sysctl.d/90-mumble-video-udp.conf` (`rmem_max`/`wmem_max` 8388608),
server restart. Proved first on the test server (64739): rb 8388608. After, on
prod, same load class, ~3,800 video datagrams/s inbound: **0 drops in 30 s**,
peak buffer use 408,384 of 8 MB — the old buffer was one burst short. Static
regions on the receiver: RMSE 0.000 for 10/10 consecutive pairs, no black
rectangles in 12 crops. Server CPU 7.2 % vs 0.03 %: it now relays what it
threw away. The stopwatch latency did not change (self-healing region), which is
why the pre-fix measurements looked fine.

This branch makes the clamp visible: server and client read the buffer back and
log the effective size with the sysctl to raise; `deploy-server.sh` warns before
starting a container on a clamped host (`--network=host` means the host's limit
is the server's). Any Linux client host has the same request and the same
default; fedora and kohaku happened to be at 4 MB already.

## 2. Receiver: the Chromebook run (open)

Real remote client (`remote1`, kohaku, i5-10210U at low clocks, 7 GB RAM with 0
free, 5 GHz WiFi −58…−62 dBm, one hairpin hop to calegix, `mtr -u` 30×: 0 %
loss, rtt 4–45 ms). The user closed it at 19:36:10 as too laggy. It was
receiving tx1's mock 1920x1080 screen and mock camera (**~19 Mbit/s down**,
~2,714 datagrams/s) and, started by the user, *sending* a real portal screen
capture and a real 720p camera.

- client socket `rb 8388608` (rmem_max was already 4 MB; not clamped) and yet
  **d 0 → 22,672; RcvbufErrors +14,914 in 105 s = 5.2 % of datagrams**. The
  process was not reading its socket fast enough. *Inferred* cause: GUI thread
  saturated by capture + JPEG encode + VP8 encode + two decodes at once (audit
  items 1, 4, 7); a clean CPU sample was not captured before the close.
- log, every 1.5–2 s: `VideoGrid: stream 2/0 lost frame continuity (15035 →
  15041), frozen until a keyframe arrives` then `Video: requesting a keyframe
  for stream 2/0`. Stream 2/0 is the VP8 camera. Keyframe requests are throttled
  to 1/s at client and server and the encoder's interval is 60 frames, so each
  loss burst costs 1–2 s of frozen picture. Tiles degrade gracefully; VP8 does
  not.
- the mock camera is incompressible noise, ~6.7 Mbit/s: harsher than any real
  webcam, but the mechanism does not depend on it.

## Sender burst shape (Windows, measured)

Real DXGI share of a 1280x800 desktop from win-2, 10 s tcpdump windows on
calegix, `drag` = 300 `SetWindowPos` moves of a 900x560 window in 10 s:

| state | pkts/s | Mbit/s |
|---|---|---|
| screen only, desktop idle | 41 | 0.30 |
| screen only, stopwatch visible | 633 | 4.5 |
| screen only, dragging a large window | 1,702 | 12.1 |
| screen + mock camera, idle | 928 | 7.7 |
| screen + mock camera, dragging | 2,169 | 16.3 |

Idle to dragging is 40x, delivered as one burst per frame with no pacing below a
single `encode()` call. That is the shape that overflowed the clamped server
buffer and the Chromebook's un-drained one. The mock camera is a constant ~6.7
Mbit/s of incompressible noise and is not representative of a webcam.

Two client bugs found on the way, both measured:

- **Shares are not re-armed after an automatic reconnect.** After the server
  restart every client reconnected within seconds, and every share stayed off
  (3 pkts/10 s). A user whose connection blips for a second silently stops
  sharing and has to notice.
- On one reconnected process, Share Camera produced neither `Sharing camera` nor
  `No camera is available`; a fresh process behaved. Not root-caused.
- (Harness note) UI Automation `TogglePattern.Toggle()` on the Share buttons
  flips the checked state without firing the QAction; only a real click starts
  a share. Worth knowing before anyone automates this UI.

## 3. Sender: heavy scenes (open, from the audit, not reproduced)

The whole sender pipeline is on the GUI thread behind a 33 ms `QTimer`; a 1080p
frame costs an 8 MB readback, a full `convertToFormat`, a copy of 135 tiles, a
byte-wise FNV over 8 MB and single-threaded JPEG per changed tile. Overrun the
timer and Qt drops ticks: the share falls to 15/10/7 fps and **the sender never
sees it** — their preview is the raw capture. 1080p is 135 tiles against a
128-unit cap, so every keyframe is two encode calls. Our Windows sender was a
mostly static 1280x800 desktop (8–12 changing tiles, 14 % CPU, ~5 Mbit/s) and
did not trip this; 1080p with large changes should be the next measurement.

## What to do next, in order

1. **Ship the clamp logging** (this branch) and put the sysctl in the deploy docs.
2. **Receiver:** move the UDP reader and decoders off the GUI thread; apply tiles
   by position, not arrival order (the watermark already allows it); make VP8
   loss cheaper (shorter keyframe interval or error-resilient mode, un-throttle
   the first keyframe request after a continuity break).
3. **Sender:** encode off the GUI thread; pace a keyframe burst across the frame
   interval; 144 px tiles or a 160 cap so 1080p is one encode call; cheaper
   change detection than a byte-wise hash.
4. **Measure time in CI:** none of the video suites measure encode wall time,
   effective fps, burst pacing or loss-to-repair latency.

## Rig notes (so this can be repeated)

Windows: settings are `%LocalAppData%\Mumble\Mumble\mumble_settings.json`;
skip wizards with `misc.audio_wizard_has_been_shown`, `video.video_wizard_shown`,
`mumble_has_quit_normally` and a passwordless PKCS12 `certificate`; launch
`mumble.exe --skip-settings-backup-prompt mumble://user@host/` from a scheduled
task as the desktop user, Interactive, Highest. Linux headless: Xvfb, cert digest
pre-trusted in `mumble.sqlite` (the SSL prompt never appears headless and the
client silently stays "Not connected"), `start-client.sh` Escapes the wizards
with xdotool. `MUMBLE_MOCK_SCREEN=1` draws a frame counter for pairing. Server
log is journald only; kernel drops never appear in it. The server's autoban
(10 connections / 120 s) bans a harness that reconnects too eagerly. The tile
name overlay covers the top of shared content and should be inset.

Two measurement traps: clients on the calegix LAN resolve `calegix.com` to
**IPv6**, so a `src 10.0.26.45` tcpdump filter never sees them (filter by the
client's UDP source port instead); and the 1920x1080 mock screen alone is a
**~17 Mbit/s** source (2,000–2,300 datagrams/s: scrolling terminal plus a
bouncing block at 31 fps), busier than most real desktops. Use a smaller
`MUMBLE_MOCK_SCREEN_SIZE` or a real desktop when the receiver is the thing
under test.
